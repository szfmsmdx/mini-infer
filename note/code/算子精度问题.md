# 算子精度问题：从失败样本找到出错的中间步骤

这篇笔记记录 mini-infer 在实现逐元素算子和反向传播时遇到的数值问题。重点不是记住哪条公式“更稳定”，而是弄清楚：**输入已经确定后，哪个中间结果先丢了精度，这个误差又怎样影响最终输出。**

截至 2026-11-20，本机 Windows CPU、PyTorch 2.11.0+cpu 环境下，10 个逐元素算子在 FP32、FP16、BF16 上的前向和反向，共 884,818 次双参考比较全部通过。这个结论不包含 RMSNorm 等组合算子；后面补测 RMSNorm 时又发现了 84 个失败。最新 CUDA 代码尚未在 GPU 编译运行验证。

## 1. 数学上等价，不代表浮点计算结果相同

浮点数既有范围限制，也有精度限制：

| dtype | 有效二进制位数（含隐藏位） | 最大有限值，约 |
| --- | ---: | ---: |
| FP16 | 11 | 65,504 |
| BF16 | 8 | 3.3895e38 |
| FP32 | 24 | 3.4028e38 |

FP16 容易超出范围；BF16 的范围接近 FP32，但相邻可表示数之间的间隔更大。两者不能都简单理解成“精度差一点的 float”。

还有一个容易忽略的区别：**kernel 内用 float 计算，不代表多个 Tensor 算子之间也一直保留 float。**

```text
FP16 Tensor → kernel 内 FP32 计算 → 写回 FP16 Tensor
                                      ↓
                               下一个算子重新读入
```

写回时已经丢掉的有效位，下一步再转成 float 也补不回来。一个表达式拆成多个 Tensor 运算，会经过多次舍入；单个 kernel 把整条公式算完，则可以只在最后舍入一次。

## 2. div 反向：先看运算顺序，不急着换类型

对于 `y = a / b`，上游梯度为 `g`：

\[
\frac{\partial L}{\partial a}=\frac{g}{b},\qquad
\frac{\partial L}{\partial b}=-\frac{ga}{b^2}
\]

公式没错，但直接计算 `b*b` 会引入本来可以避免的溢出。

以 `a=1, b=300, g=1` 为例：

```text
b*b = 90000 → 超过 FP16 最大值，写回后是 Inf
-g*a/Inf   → 0

数学结果   → -1/90000 ≈ -1.1111e-5
```

去掉平方以后，还要检查分子。例如 `a=60000, b=2, g=3`：`g*a=180000` 也会先溢出，尽管最终梯度 `-45000` 可以用 FP16 表示。

目前采用的顺序是：

```cpp
-output_grad * ((a / b) / b)
```

它避开了显式的 `b²` 和提前计算 `g*a`。这不代表它对所有浮点输入都是最优顺序；只说明解决这类问题时，应先沿计算顺序检查中间范围，而不是看到误差就把所有步骤改成 double。

## 3. exp 反向：保存输出没问题，但要接受输出 dtype 的范围

exp 的导数是自身，因此保存前向输出 `y` 后，可以计算：

```cpp
dx = output_grad * y;
```

保存的是 `y.detach()`，共享数据存储，不再复制一份输出数据，也不通过输出的 Autograd 元数据形成持有环。它会延长数据的存活时间；“没有复制”不等于“不会影响显存释放时间”。

数值问题在于：如果 `y` 已经溢出，反向不能再从它恢复有限结果。

一个教学例子：FP16 的 `x=12`，`exp(12)≈162754.8`，写回 FP16 后是 Inf。若 `g=0.1`，数学上的乘积约为 16275.5，本可以表示；但使用保存的 FP16 输出计算时仍会得到 Inf。

这促使我们重新区分两件事：

- 数学公式最终结果可以表示，不代表执行中间步骤时不会溢出。
- 测试要求对齐 Torch，也不等于要求在所有极端输入上都达到高精度数学参考。

最终保留基于输出的 exp 反向，没有为极端样本引入 double 重算。测试改为分别比较数学参考与同 dtype、同设备的 Torch，保留两种对照结果。

## 4. sigmoid 反向：前向误差很小，也可能被梯度放大

BF16 的一个实际失败样本：

```text
x = -92
g = BF16 最大有限值，约 3.3895e38

修改前梯度： 0.0311279296875
数学参考：   0.03759765625（舍入到 BF16 后）
Torch：      0
```

原因是 `sigmoid(-92)≈1.10894e-40`，已经落在 BF16 的次正规数范围。BF16 最小正次正规数约为 `9.18355e-41`，保存的输出只能落到这些离散位置上。

前向的绝对误差约为 `1e-41`，很容易满足 `atol=1e-5`；乘上约 `1e38` 的梯度后，误差却不再小。因此，**前向通过不能推出反向也通过。**

修改后的计算方式：

```cpp
float t = expf(-fabsf(x));
float denominator = 1.0f + t;
float dx = (g * t) / (denominator * denominator);
```

从输入重新计算导数，整段保持 FP32，最后写回原 dtype。不再用已舍入的低精度输出计算导数。先计算 `g*t`，也避免先把很小的导数写回低精度 Tensor。

CPU 实测：原先 BF16 的 4 个失败全部修复，三种 dtype 各 5,330 个反向样本全部通过数学参考。原有输入、输出版本检查仍然保留。

## 5. rsqrt 反向：重复乘法放大中间舍入误差

令 `y = 1/sqrt(x)`，则输入梯度为 `-0.5*g*y³`。原实现复用 Tensor 算子：

```cpp
const Tensor y = rsqrt(x);
return {(-0.5f * y) * output_grad * y * y};
```

实际 FP16 样本 `x=0.2445068359375, g=-0.5` 的中间结果：

```text
y = rsqrt(x) → 2.021484375
-0.5*y       → -1.0107421875
再乘 g       → 0.50537109375
再乘 y       → 1.021484375
再乘 y       → 2.064453125

数学参考舍入后：2.068359375
Torch：        2.0703125
```

这些箭头之间会写回 FP16。误差既来自 `y` 的舍入，也来自后续乘法。

修复时没有改变导数公式，只改计算位置：在逐元素 CPU/CUDA 反向中，以 FP32 重新计算 `y`，再计算 `((-0.5*y)*g)*y*y`，最后一次写回原 dtype。

CPU 实测：FP16 的 215 个失败、BF16 的 1 个失败全部消失；FP32/FP16/BF16 的 7,480/5,110/7,320 个反向样本都通过数学参考。

排查时还有一个容易误读的统计：原先有 130 个失败涉及 Inf/NaN，**非有限结果来自 Torch，不是我们的输出**。例如我们算出 24368，数学参考为 24400，Torch 为 Inf。我们的结果虽然比 Torch 更接近数学值，但仍超过数学容差，也不与 Torch 对齐，因此两道检查都失败。

## 6. SiLU：不能只为消灭失败样本就扩大到 double

### 前向：避免低精度 sigmoid 中间 Tensor

`silu(x)=x*sigmoid(x)`。拆成两个 Tensor 算子时，sigmoid 的结果可能提前舍入或下溢。最终改成逐元素执行完整前向公式。

当前前向实现通常使用 FP32；`x < -80` 的负尾部仍使用 double 计算 `x*exp(x)/(1+exp(x))`，避免指数在乘 x 前失去数值。**这是现有前向代码的分支，不要和后面讨论后撤回的反向 double 方案混淆。**

### 反向：低精度舍入之外，还有相消

令 `s=sigmoid(x)`，数学导数为：

\[
D(x)=s+xs(1-s)
\]

改动前共有 519 个失败：FP32 70 个、FP16 259 个、BF16 190 个。

两个 16 位类型主要受中间 Tensor 舍入影响。FP32 的失败则集中在两个位置：64 个在导数零点附近，另外 6 个在负尾部。

对负数输入令 `t=exp(x)`，导数可以写成：

\[
D(x)=\frac{t(1+x+t)}{(1+t)^2}
\]

零点满足 `1+x+exp(x)=0`，约为 `x₀=-1.278464542761074`。附近有：

\[
D(x)\approx0.2178117057(x-x_0)
\]

这时两个大小约为 0.22 的项相减，可能只剩 `1e-7` 量级的导数。相减暴露了中间值已有的舍入误差；再乘上巨大梯度，就能形成明显的最终误差。

负尾部的实际样本是 `x≈-103.9720764, g≈3.4028e38`。`exp(x)` 接近 FP32 最小次正规数的一半，舍入后几乎翻倍：我们的梯度约为 `-4.91142e-5`，数学参考约为 `-2.45505e-5`，Torch 返回零。

这些例子说明误差的来源，但不直接决定产品实现必须使用 double。

### 最终采用 Torch 的计算方式

我们先模拟过在负尾部和零点附近使用 double，也讨论过让全部负数进入 double。这两种方案都能减少失败，但会增加计算成本，实际 GPU 性能尚未测量。仅为了让数学参考通过，就给整个负数区域增加 FP64 计算，不符合当前对齐 Torch 的目标。

核对本机 Torch 版本对应的 CPU/CUDA 源码后，最终采用它的计算顺序：

```cpp
float s = 1.0f / (1.0f + expf(-x));
float dx = (g * s) * (1.0f + x * (1.0f - s));
```

FP16、BF16、FP32 输入都在 FP32 中完成反向，最后写回原 dtype。不按 x 分区，也不使用 double。代码放在现有 `ops/elementwise/elementwise.cpp` 和 `ops/elementwise/cuda.cu`，没有新增每个算子独立的文件夹。

Python 公式模拟时还剩 2 个 FP32 失败；实际 C++ 导出结果中剩余 0 个。模拟不能代替真实实现的验证，标量/向量指数实现和编译方式都会影响浮点结果。

每种 dtype 都有 5,330 个 SiLU 反向样本，最终 CPU 结果为：

| dtype | 数学参考通过 | 仅 Torch 对齐通过 | 两者均失败 |
| --- | ---: | ---: | ---: |
| FP32 | 5,234 | 96 | 0 |
| FP16 | 5,330 | 0 | 0 |
| BF16 | 5,306 | 24 | 0 |

## 7. 测试怎么判，才能区分代码问题和浮点限制？

先检查输出 shape、dtype、device。结构不对不能用数值容差放行。数值比较使用同一份输入和上游梯度：

```text
mini-infer 导出输入与结果的原始位编码
    ├─ FP64 独立数学公式，最后舍入到目标 dtype
    └─ 同 dtype、同设备的 Torch 前向和反向
                         ↓
逐元素：数学参考达标，或者 Torch 对齐 → 通过
        两者都不满足                  → 记录失败
```

数学参考不是无限精度，而是在当前输入范围内使用 FP64 的独立解析公式。Torch 环境不锁版本，只要求能够导入；报告记录实际版本。CPU 对 CPU，CUDA 对 CUDA，不能用 CPU 结果冒充 GPU 验证。

有限值使用：

\[
|actual-reference|\le atol+rtol\,|reference|
\]

| dtype | rtol | atol |
| --- | ---: | ---: |
| FP32 | 1.3e-6 | 1e-5 |
| FP16 | 1e-3 | 1e-5 |
| BF16 | 1.6e-2 | 1e-5 |

同位置 NaN、同号 Inf 可以视为一致。仅仅“比 Torch 更接近数学值”，但两项比较都超容差，仍然是失败元素；不能在看到结果以后临时换标准。

### 样本分组，不把所有失败塞进一个百分比

以 SiLU 每种 dtype 为例：

| 分组 | 数量 | 来源 | 验收 |
| --- | ---: | --- | --- |
| 基础 | 513 | 手写输入与固定种子补齐的基础样本 | 全部通过 |
| 边界 | 720 | 72 个边界输入 × 10 个上游梯度 | 全部通过 |
| 随机 | 4,097 | 固定种子的伪随机样本 | 至少 99.5% 通过 |

边界输入包括指定常量、由 dtype 范围计算出的指数边界，以及 SiLU 导数零点附近的取样。它们是手工设计的规则，不是照搬 Torch 的测试集，也不是 720 组逐条写死。转成目标 dtype 后，部分输入可能重合。

随机组最多允许 20 个失败：`floor(4097*0.005)=20`。失败 21 个就不通过。基础、边界和另外测试的特殊值组必须全部通过，不能借用随机组额度。不同算子、dtype、前向和每个输入梯度分别验收。

不能用全局通过率替代这个规则：SiLU 还存在 519 个失败时，全局通过率已经约为 99.94%。其他算子的大量成功样本会掩盖 SiLU 的问题。

所有失败下标都会保留，即使随机组最终被验收通过。输入 Tensor 也不按组切开重算，只在结果上分组统计，避免改变 Torch 向量化路径。

## 8. 补测 RMSNorm：基础算子全过，组合仍可能出错

目前的 RMSNorm 是组合实现：

```cpp
auto inv_rms = ((x * x).mean(-1, true) + eps).rsqrt();
return (x * inv_rms) * weight;
```

它已经能建图并反传，不缺 Module 实现。新测试补的是整个归一化过程的数值验证：一维、二维、三维、非连续输入和权重、单特征、零输入、不同 eps、小输入、大输入和较宽特征维，并检查输入梯度与权重梯度。

本机新增的 10 个固定案例 × 3 种 dtype，共 5,166 次比较结果：

| dtype | 前向失败 | 输入梯度失败 | 权重梯度失败 |
| --- | ---: | ---: | ---: |
| FP32 | 0 | 0 | 0 |
| FP16 | 11 | 36 | 30 |
| BF16 | 0 | 5 | 2 |

结构测试通过，精度测试有 84 个失败。这些是固定回归/边界案例，不使用随机组的 0.5% 额度。

一个实际 FP16 前向失败输入为 `x=-450`：

```text
x*x = 202500 → 写回 FP16 后为 Inf
行内均值    → Inf
倒数平方根  → 0
最终输出    → 0，而数学参考和 Torch 约为 1.76953
```

单独测 FP16 乘法时，202500 超出该类型范围，写回 Inf 符合乘法接口的 dtype 语义。但 RMSNorm 的数学结果仍然可以表示。问题是组合过程把平方结果提前写回了低精度，而不是乘法 kernel 的 float 运算出错。

修复方向是让 RMSNorm 的平方、归约、归一化以及反向中间量保持 FP32，最后才写回输出和梯度。对同一批样本做 FP32 整段计算模拟后，三种 dtype 的失败都变为零；**目前只是模拟，RMSNorm 实现尚未修改**。

## 9. 后续排查沿用这条顺序

1. 固定输入的实际位编码、dtype、布局、eps 和上游梯度，先保证双方算的是同一个问题。
2. 区分结构错误、有限值超差、非有限值不一致。报告中出现 Inf/NaN 时，要查清是哪一方产生的。
3. 把表达式拆成中间步骤，标出每次写回的 dtype；寻找第一次溢出、下溢或明显舍入。
4. 核对参考公式与实际框架实现。先考虑计算顺序、FP32 中间计算或完整逐元素 kernel，不默认扩大到 double。
5. 用原样本复测，并把修复过的反例加入回归。不要删除失败案例或随结果调整容差。
